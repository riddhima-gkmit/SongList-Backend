    Optimization¶

    Tools¶

    • django-silk: HTTP and SQL profiler integrated into Django.
      Use when you want to inspect per-request SQL, spot N+1 queries, and see slow views locally or on a staging server (/silk/).

    • pyinstrument: Sampling profiler for Python call stacks.
      Use when a request is slow but not obviously DB-bound and you need to see which functions and lines consume most wall time.

    • New Relic APM: Production-grade monitoring.
      Use when you need real-time performance charts, error traces, slow-transaction breakdowns, and database time in your live environment.

    • Locust: HTTP load-testing tool.
      Use when you want to simulate concurrent listeners/admins (e.g. browsing playlists, requesting songs) and measure throughput, latency, and failure rates.

    Query Optimization Best Practices¶

    1. Use select_related for single-object relations
      Apply it to foreign key / one-to-one relationships (e.g. requester, tenant, subscription, song) when serializing lists. This pushes joins into a single SQL query and avoids N+1 on detail fields.

    2. Use prefetch_related for collections
      For many-to-many and reverse foreign key relationships (e.g. playlist songs, tenant users), use prefetch_related to fetch related rows in a small, fixed number of queries.

    3. Annotate instead of per-row .count()
      For things like song_count per genre or user_count per tenant, prefer annotate(Count(...)) on the queryset rather than calling .count() inside a serializer or property.

    4. Project only what you need
      When returning large lists, use .only() or .values() / .values_list() if you truly only need a subset of fields.

    Optimization Techniques in SongList Backend¶

    We use several layers of optimization:

    • Database indexing
    • Primary keys (UUIDs) and common filter fields (e.g. tenant_id, deleted_at, status) are indexed by default or via model constraints.

    • Where possible, queries are written to align with these indices (e.g. filtering on deleted_at__isnull=True rather than scanning soft-deleted rows).

    • N+1 query prevention

    • List endpoints are progressively being updated to use select_related/prefetch_related for related objects accessed in serializers.

    • Properties that compute counts (user_count, genre song counts, etc.) should be moved to queryset annotations to avoid per-row queries.

    • Redis caching

    • Frequently accessed, read-heavy lists (such as tenant songs or genres) are cached in Redis behind helper functions and cache keys.

    • Cache invalidation hooks are used on create/update/delete operations for those resources.

    • Background work via Celery

    • Non-critical and heavier tasks (email notifications, payment/plan reconciliation, etc.) are pushed to Celery workers so that API responses stay fast for end users.

    Load Testing with Locust¶

    You can run load tests against a local or staging environment using Locust:

    locust -f locustfile.py
