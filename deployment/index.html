    Deployments¶

    Overview¶

    SongList Backend uses a fully automated CI/CD pipeline built on GitHub Actions. Every push to the main or ci-cd branches (or merged pull request into main) triggers a test run, a Docker image build, and deployment to an AWS EC2 instance.

    The production runtime is a Docker Compose stack with multiple services: a Django/Gunicorn web server, PostgreSQL, Redis, a Celery worker, and Celery Beat, plus Nginx and a helper Certbot container. Nginx acts as a reverse proxy and serves static files directly.

    Flow¶

    Tools for CI/CD - Docker¶

    • Docker: Containerizing the application for consistency.
    • Docker Compose: Orchestrating our multi-container architecture.
    • GitHub Actions: Primary CI/CD automation platform.
    • GHCR: Storing and managing our Docker images.
    • uv: Fast Python package manager for dependencies.
    • Gunicorn: Production WSGI server running our Django app.
    • New Relic: Provides robust application performance monitoring in production.

    Pipeline Triggers¶

    Defined in .github/workflows/deploy.yml:

    Event Condition
    push Any push to main or ci-cd branch
    pull_request PR closed against main
    workflow_dispatch Manual trigger from the GitHub Actions UI

    CI Test Job (test)¶

    Steps¶

    # Step Detail
    1 Checkout repository actions/checkout@v4
    2 Install uv pip install uv
    3 Set up Python 3.13 actions/setup-python@v5
    4 Install dependencies uv sync --frozen (locked versions)
    5 Run Pytest uv run pytest --tb=short -v — full suite against Postgres + Redis service containers

    Gate: The build-and-deploy job only runs if this job succeeds.

    Build & Push Job (build-and-deploy)¶

    Requires packages: write permission to push to GHCR.

    Build steps¶

    # Step Action
    1 Login to GHCR docker/login-action@v3 using GITHUB_TOKEN
    2 Extract metadata docker/metadata-action@v5 → produces sha-{SHA} and latest tags
    3 Set up Docker Buildx docker/setup-buildx-action@v3
    4 Build & push docker/build-push-action@v6 with registry cache and inline cache

    Deploy to EC2 (inline script)¶

    After the image is pushed, the workflow SSHs into EC2 (appleboy/ssh-action@v1, 600s timeout) and runs an inline Bash script. All GitHub Secrets are written into a .env file before docker compose is invoked.

    The script is idempotent — every deploy:

    1. Ensures /opt/songlist exists and is owned by the deploy user.
    2. Clones the repository on first deploy, or runs git fetch + git reset --hard origin/<branch> on subsequent deploys.
    3. Writes .env from GitHub Secrets (database, Redis, email, Razorpay, New Relic, etc.).
    4. Logs in to GHCR using a personal access token (GHCR_PAT).
    5. Pulls the latest image:
    docker pull ghcr.io/<owner>/songlist-backend:latest
    1. Starts or updates the Docker Compose stack:
    docker compose up -d --no-build
    1. Cleans up dangling images:
    docker image prune -f

    Runtime stack (Docker Compose)¶

    On EC2, docker compose uses the docker-compose.yml file in the repo root. The main services are:

    Service Description
    web Django + Gunicorn, started via newrelic-admin run-program, serves the API on port 8000 inside the compose network
    celery-worker Celery worker process, also wrapped in newrelic-admin run-program
    celery-beat Celery Beat scheduler, wrapped in newrelic-admin run-program
    db PostgreSQL 16 with postgres_data volume and pg_isready healthcheck
    redis Redis 7 used for cache and Celery broker/result backend
    nginx Reverse proxy listening on ports 80/443, serving /static and /media and proxying to web:8000
    certbot Helper container for obtaining/renewing Let’s Encrypt certificates (invoked manually)

    The Nginx config lives at deploy/nginx/conf.d/songlist.conf and:

    • Serves the ACME HTTP-01 challenge from /var/www/certbot.
    • Serves /static/ and /media/ from the static_data and media_data volumes.
    • Proxies all other traffic to the web service.

    DNS, Security Groups, and SSL¶

    In production there is typically some surrounding infrastructure in front of the Docker stack:

    1. Configure DNS
    2. Point a domain like api.example.com (A or CNAME record) to your EC2 instance, or to a load balancer in front of it.

    3. Once DNS propagates, requests to that hostname will reach your Nginx container on the EC2 host.

    4. Lock down network access (security groups / firewall)

    5. Allow inbound 80/tcp and 443/tcp from the internet so HTTP/HTTPS traffic can reach Nginx.
    6. Optionally, restrict 22/tcp (SSH) so only a bastion host or trusted IP ranges can connect.

    Running Certbot manually¶

    The certbot service in docker-compose.yml is intentionally minimal and does not auto-provision certificates. A typical manual flow on EC2 is:

    1. Verify Nginx is serving the ACME challenge path

    2. Ensure the stack is up and that Nginx is serving /.well-known/acme-challenge/ from /var/www/certbot as configured in deploy/nginx/conf.d/songlist.conf.

    3. Request a certificate with Certbot

    4. Run Certbot inside the certbot container, pointing it at the same webroot:

    ```bash docker compose run --rm certbot certonly \ --webroot -w /var/www/certbot \ -d api.example.com \ --email you@example.com \ --agree-tos --no-eff-email
